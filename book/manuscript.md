## OpenCode 是什麼

### 本節目標

讀完本章後，你應能解釋 OpenCode 與一般聊天工具、程式碼補全工具的差異，畫出主要元件的關係，並在不修改檔案的情況下完成第一次安全探索。

### 從聊天到代理

聊天工具通常只產生文字；程式設計代理還要觀察專案、讀取檔案、執行測試、修改程式，再根據結果調整方案。OpenCode 將這個過程組織成代理迴圈（Agent Loop）：模型提出下一步，平台檢查權限並執行工具，工具結果再回到模型上下文。

這個分工避免把模型當成擁有無限權限的使用者。模型只能提出 Tool Call；真正是否讀檔、寫檔、執行命令或呼叫外部服務，應由平台和使用者的權限政策決定。

### 核心元件

- **Provider**：提供模型服務、認證與帳務。
- **Model**：Provider 中的具體模型版本。
- **Session**：保存訊息、工具呼叫、結果與工作狀態。
- **Context**：送給模型的系統指示、規則、歷史與資料片段。
- **Tool**：執行讀檔、搜尋、測試或其他動作的受控介面。
- **Skill／Command**：保存可重用的工作流程與提示。
- **MCP**：以協定連接外部資料與服務。
- **Extension／Plugin**：在核心之外加入事件、工具或整合能力。

元件的邊界是實務上的設計工具。把「如何審查 diff」做成 Skill，把「執行測試」做成 Tool，把「連接 GitHub」交給 MCP，能分別測試、升級和撤銷。

### 擴充優先的理由

模型、Provider、UI 與外部服務都會變動。如果所有能力都寫死在核心，任何一個服務改版都可能影響整個系統。精簡核心只保留 Session、上下文、權限與事件等穩定協調能力；變動的能力則在外部組合。

擴充優先並不表示功能越多越好。每個擴充仍須說明輸入、輸出、權限、版本、生命週期與失敗行為。沒有清楚邊界的「萬能 Agent」通常難以測試，也難以知道錯誤發生在哪一層。

### 一次請求的資料流

```text
使用者目標
  → Session 與設定
  → Context 建構
  → Provider／Model
  → Tool Call 或文字回覆
  → 權限檢查與工具執行
  → 工具結果回到 Session
  → 下一輪模型請求或完成回覆
```

這條資料流也是除錯順序。模型選錯時查 Provider 與設定；工具結果錯時查工具輸入與工作目錄；恢復失敗時查 Session 與檔案系統，而不是只修改 Prompt。

### 第一次安全探索

在不含機密的 Git 專案根目錄執行：

```bash
opencode --version
opencode run "只列出主要目錄與測試指令，不要修改檔案，也不要執行命令"
```

把代理的回答與實際目錄比較。若它要求超出限制的工具，拒絕請求；不要因它的說明看似合理就自動批准。

### 本節練習

1. 為一個專案畫出 Provider、Session、Context、Tool 的資料流。
2. 將「產生 Commit 訊息」分別用 Prompt 和 Skill 描述，指出兩者差異。
3. 設計一個只能讀取 `src/` 的任務，列出平台應阻擋的三種操作。

### 小結

OpenCode 是協調模型、上下文與受控能力的代理環境。先理解元件責任與資料流，再學習設定和擴充，能避免把所有問題歸咎於模型。

## 安裝、啟動與基本操作

### 本節目標

本章建立可重現、可還原的工作環境，完成第一次唯讀任務，並學會以版本、工作目錄、認證與設定檔的順序排查啟動問題。

### 安裝前檢查

OpenCode 的安裝方式依作業系統與版本而異，應先參考官方安裝頁，再驗證：

```bash
opencode --version
opencode --help
```

Windows WSL2 使用者還要確認目前是在 WSL 或 Windows 端、檔案是否位於預期的掛載路徑，以及是否需要 WSLg 顯示 GUI。不要把 Linux 家目錄、Windows 掛載目錄與專案路徑混為一談。

### 建立練習專案

```bash
mkdir opencode-lab && cd opencode-lab
git init
mkdir src tests
printf '# OpenCode Lab\n' > README.md
printf 'def add(a, b):\n    return a + b\n' > src/math.py
git add . && git commit -m 'Create practice project'
```

正式專案開始前，先執行 `git status --short`，把未提交的個人修改保存好。代理的每次修改都應能由 Git 審查或還原。

### 互動與一次性任務

在專案根目錄執行 `opencode` 可進入互動介面；`opencode run "任務"` 適合腳本與教學。第一次只做唯讀探索：

```bash
opencode run "找出 add 函式，提出三個測試案例；不要修改檔案"
```

之後自行檢查檔案、測試目錄與代理引用的路徑。只有在目標清楚且變更可還原時，才批准寫檔或執行測試。

### 啟動排查流程

遇到問題時依序檢查：

1. `command -v opencode` 是否找到正確執行檔。
2. `opencode --version` 是否符合書中技術基線。
3. `pwd` 是否為專案根目錄。
4. Provider 是否完成登入，模型是否在 `opencode models` 清單。
5. `opencode.json`／`.jsonc` 是否為合法 JSONC。
6. 是否有命令列或環境變數覆寫設定。

使用 `opencode debug --help` 查詢該版本支援的診斷功能。不要一遇到設定錯誤就刪除 Session；先保存錯誤訊息與目前檔案，才能重現問題。

### 安全基線

練習專案不放 API Key、客戶資料或生產憑證。為寫入任務建立 Git 分支，先讓代理列出預計修改檔案，再用 `git diff` 檢查。測試失敗時保留輸出，不要讓代理自行刪除測試來取得綠燈。

### 本節實作

進入 `examples/02-practice-project/`，建立練習專案並完成一次唯讀探索。把命令、版本與預期結果記入 README，讓另一位讀者能在相同目錄重做。

### 本節練習

- 在乾淨專案完成一次唯讀任務與一次測試任務。
- 故意從子目錄啟動，觀察設定與規則是否改變。
- 以 `git diff --check` 找出格式問題，並記錄修復方式。

### 小結

可重現的工作目錄、乾淨的 Git 狀態與小型任務，是使用代理的安全基線。安裝完成後，還要驗證版本、Provider、模型與設定是否真的生效。

## 從請求到回應：Agent Loop

### 本節目標

本章逐步拆解代理迴圈，理解模型、工具、權限和上下文如何往返，並知道何時應中斷而不是繼續批准。

### 六個步驟

1. 使用者提出目標、範圍與限制。
2. OpenCode 建立或恢復 Session。
3. 平台組合系統指示、專案規則、歷史與相關檔案。
4. Provider 將 Context 送給 Model。
5. Model 回傳文字或提出 Tool Call；平台檢查權限後執行。
6. 工具結果寫回 Session，模型決定下一步或完成回答。

模型的「建議」與平台的「執行」是兩件事。這個邊界讓使用者可以拒絕危險工具，也讓系統能對所有 Client 套用相同的權限規則。

### 由唯讀任務開始

```bash
opencode run "找出所有測試檔案，列出測試指令；不要修改檔案，也不要執行命令"
```

任務同時提供正面目標和負面限制。完成後，以自己的命令驗證檔案清單；不要只因模型回答流暢，就認為它讀到了正確的專案。

### 工具合約與結果

工具應說明輸入型別、輸出格式、權限、錯誤與副作用。搜尋工具回傳檔案和行號即可；測試工具回傳命令、退出狀態和關鍵錯誤即可。把完整建置日誌全部送進上下文，會浪費 Token 並遮蔽真正問題。

對修改任務採取探索、計畫、修改、測試、審查五階段。每階段有一個可驗收出口，例如「列出將修改的檔案」或「測試命令退出碼為零」。

### 錯誤與中斷

工具失敗、Provider 逾時、權限拒絕與使用者取消都可能結束迴圈。網路逾時可以有限次重試；權限拒絕或破壞性命令不應盲目重試。中斷後先看 Git diff、背景程序與外部服務，再決定繼續、分支或重開 Session。

### 觀察一次完整工作

在測試專案要求代理「先提出計畫，不要修改」，記錄它讀取的檔案與請求的工具。批准一個低風險讀取工具後，再拒絕一個不必要的寫入工具。這個演練能讓你看見權限檢查是迴圈的一部分，而不是事後補救。

### 本節練習

1. 畫出一個測試修正任務的 Agent Loop。
2. 為一個 `run_tests` 工具定義成功、失敗、逾時與取消輸出。
3. 列出三個應立即拒絕的 Tool Call，並說明原因。

### 小結

Agent Loop 是「模型提出、平台執行、結果回饋」的循環。清楚的工具合約、有限的上下文、可驗收的階段與可中斷的權限，決定了代理是否可靠。

## 設定檔放哪裡

### 本節目標

本章解決初學者最常遇到的問題：設定檔究竟放在哪裡、哪一份會生效、LLM 選擇寫在哪裡，以及如何在不洩漏憑證的情況下共享專案設定。

### 先確認版本與工作目錄

設定鍵與搜尋規則可能隨 OpenCode 版本改變，因此不要直接套用未標示版本的網路文章。先執行：

```bash
pwd
opencode --version
opencode --help
```

工作目錄應是專案根目錄，也就是包含 `.git` 的目錄，而不是 `src/`、`dist/` 或暫存目錄。代理若在錯誤目錄啟動，可能讀不到 `AGENTS.md`，也可能把另一個專案當成目前工作範圍。

### 全域設定放哪裡

個人偏好通常放在使用者設定目錄。Linux 常見位置是：

```text
~/.config/opencode/opencode.json
~/.config/opencode/opencode.jsonc
```

Windows 與 macOS 的實際路徑可能不同，請以當前版本官方文件為準。全域設定適合放個人常用模型、顯示偏好或本機工具選項；不適合放團隊規則與秘密。

檢查檔案是否存在：

```bash
ls -la ~/.config/opencode/
```

### 專案設定放哪裡

可共享的設定放在：

```text
<專案根目錄>/opencode.json
<專案根目錄>/opencode.jsonc
```

例如：

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "model": "provider/model-name"
}
```

`provider/model-name` 是佔位值，必須替換成 `opencode models` 顯示且帳號可用的模型 ID。專案設定應只包含團隊可以共享的內容，不應包含 API Key、個人絕對路徑或客戶資料。

### `AGENTS.md` 與 `.opencode/`

`AGENTS.md` 適合描述人類可讀的工作規則：測試命令、格式化工具、目錄責任、不可修改的檔案與完成定義。它不是權限邊界，因此不能取代工具層的批准與限制。

自訂 Agent、Command、Skill 與 Plugin 的目錄與檔名會依 OpenCode 版本及功能而異；使用前先查官方文件。把這類資源放在專案內的好處是可版本控制，但必須審查其 Prompt 與權限。

### 設定優先順序的排查方法

不同來源同時設定同一個欄位時，先不要猜哪份檔案優先。建立最小測試專案，只保留一個設定來源，記錄結果，再逐一加入全域設定、專案設定、命令列選項與環境變數。每次只改一項，才能知道真正的覆寫來源。

當模型不是預期選擇時，依序檢查：啟動目錄、專案設定、全域設定、`-m/--model` 命令列選項、Provider 認證與模型 ID。把版本、命令與結果寫入問題報告，比截取一段模糊錯誤更有用。

### 安全設定檢查

提交前執行：

```bash
git diff --check
git status --short
git grep -n -i -E 'api[_-]?key|token|secret|password' -- ':!*.lock' || true
```

最後一個命令只能做初步搜尋，不能取代秘密掃描工具。若 API Key 曾經提交，刪除檔案並不足夠，還必須撤銷並重新產生憑證。

### 本節實作

進入 `examples/04-config/`，複製範例設定到一個測試專案，加入 `AGENTS.md`，再以唯讀任務確認代理能看見規則。不要在正式專案第一次測試新的 Provider 或 Plugin。

### 本節練習

1. 分別建立全域與專案設定，記錄哪一個模型實際生效。
2. 寫一份 `AGENTS.md`，列出測試命令與禁止修改的路徑。
3. 故意輸入不存在的模型 ID，記錄錯誤並說明如何恢復。

### 小結

全域設定服務個人偏好，專案根目錄設定服務團隊共識，`AGENTS.md` 描述工作規則。設定問題應以最小實驗排查，憑證則永遠與可共享設定分離。

## LLM Provider 與模型選擇

### 本節目標

本章說明 Provider、Model 與認證的關係，提供一至三個初學者選擇，並建立可比較、可切換、可控成本的模型策略。

### Provider、Model 與憑證

Provider 是模型服務與帳務的來源；Model 是該 Provider 中的具體版本；憑證則授權 OpenCode 發出請求。三者分開後，同一套 Session、Tool 與 Skill 就能在不同模型間測試。

先查看當前安裝支援的指令：

```bash
opencode providers
opencode models
opencode models <provider>
```

實際 Provider 名稱、登入流程與模型 ID 會變動，書中只使用 `provider/model-name` 代表格式。

### 初學者的三個方向

**Claude Sonnet 系列**適合一般程式開發、重構、除錯與工具協作；可作為追求平衡的主力模型。**OpenAI GPT 系列**適合多用途開發、文件與既有服務整合；先選帳號可用且價格清楚的穩定版本。**Gemini Pro 系列**適合長文件或大型程式庫探索；仍應以實測的工具呼叫品質決定。

初學者不需要三個都訂閱。先選一個能穩定完成「讀程式、修改小功能、執行測試、解釋 diff」的模型，使用一週後再評估。模型版本與價格會更新，因此出版內容應附驗證日期，並把當前 ID 放在 GitHub 範例而非正文硬編碼。

### 專案設定與單次切換

在專案根目錄的 `opencode.jsonc` 設定預設模型：

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "model": "provider/model-name"
}
```

只想針對一次任務切換時，使用命令列選項：

```bash
opencode run -m provider/model-name "分析測試失敗原因，不要修改檔案"
```

全域預設適合個人習慣，專案設定適合團隊共識，命令列覆寫適合比較實驗。不要把個人憑證或費用資訊提交到專案設定。

### 用案例評估模型

建立五到十個固定任務：目錄導覽、單檔修正、跨檔重構、測試失敗分析、程式碼審查。每次只更換模型，固定 Prompt、工作目錄與測試資料，記錄完成率、人工修改量、工具錯誤、耗時、Token 與費用。

「回答看起來合理」不是通過條件。程式任務至少要以測試、型別檢查、Lint 或人工 diff 驗證；文件任務則要檢查引用是否真的存在。

### Fallback 與資料政策

Provider 暫時失效時，先保存 Session 與測試結果，再切換備援模型。切換後重新驗證重要輸出，因為不同模型可能選擇不同工具或修改策略。公司專案還要確認原始碼、Issue、日誌與工具結果是否允許傳送至外部服務；敏感資料應遮蔽、縮小範圍或改用符合政策的本機方案。

3. 寫出 Provider 失效時的恢復步驟與不可傳送的資料清單。

### 小結

模型是可替換的服務元件。初學者先選一個主力模型，以固定案例和測試評估，再因成本、長上下文、備援或隱私需求增加其他模型。



# 工作階段與上下文

<!-- 正式稿章節；範例與勘誤見 https://github.com/t945935/opencode-deep-dive -->

## Session、訊息樹與上下文

### 本節目標

本章解釋工作階段（Session）如何保存代理工作、訊息樹如何表達分支，以及上下文壓縮為何會影響長任務。最後建立一份可恢復的交接摘要。

### Session 保存什麼

Session 通常包含使用者訊息、模型回覆、工具呼叫、工具結果及相關狀態。它保存的是代理工作的歷史，不是檔案系統的快照；Session 恢復後，檔案可能已被其他人或程序改變，因此仍須重新檢查 Git 狀態。

工作開始時記錄專案路徑、分支、模型與目標。里程碑完成時記錄已修改檔案、測試命令、測試結果、未完成工作與風險。這些資訊應放在可讀檔案或 Session 摘要中，而非只留在人的記憶裡。

### 訊息樹與分支

訊息樹允許從較早節點嘗試另一種方案。若原方案保留，分支可以比較兩組模型回覆與工具結果；但分支不會自動隔離實際檔案。需要並行嘗試時，使用 Git branch、worktree 或獨立複本，否則兩條代理工作可能互相覆寫。

### 上下文由什麼組成

模型看到的上下文可能包括系統指示、`AGENTS.md`、設定、使用者訊息、歷史對話、檔案片段與工具輸出。讀取整個建置目錄或大型日誌會浪費 Token，還可能遮蔽真正重要的錯誤。先搜尋，再讀取相關片段；讓工具輸出包含摘要、退出狀態與必要位置。

### 壓縮與摘要

當上下文接近模型視窗上限，平台可能壓縮早期訊息。摘要若漏掉限制或測試結果，代理會重複工作或誤判狀態。建議在每個里程碑留下固定格式：

```text
目標：
已完成：
已修改檔案：
測試與結果：
尚未完成：
已知風險：
下一步：
```

摘要不是證據的替代品；重要結果仍應能由檔案、Git 或測試重新驗證。

### 恢復與分支

繼續最近工作可使用：

```bash
opencode --continue
```

要指定工作階段：

```bash
opencode --session <session-id>
```

要嘗試不同方向，可搭配 `--fork`。恢復前先檢查 `git status`、目前分支與工作目錄，再把交接摘要放進第一個 Prompt。若需求已改變或上下文不可信，建立新 Session 往往比修補舊對話更安全。

### 本節實作

在 `examples/06-session-context/` 先執行唯讀任務，記下 Session ID；建立里程碑摘要後分支一次，分別執行兩種方案，最後以測試和 Git diff 選擇結果。

### 本節練習

1. 找出一個過長的工具輸出，設計更精簡的回傳格式。
2. 實作三個里程碑摘要，模擬壓縮後恢復工作。
3. 比較「繼續原 Session」與「建立新 Session」的風險。

### 小結

Session 保存歷史，上下文決定模型當下看見什麼，Git 保存實際變更。三者各有責任；可恢復的工作需要摘要、證據與檔案隔離。

## 中斷、停止與重新開始

### 本節目標

中斷是代理控制能力的一部分。讀者將學會判斷何時停止、停止後檢查哪些副作用，以及何時繼續、分支或重新開始。

### 應該中斷的時機

當代理準備修改範圍外的檔案、執行不理解的命令、讀取機密、反覆重試、偏離需求或產生高額請求時，立即停止。不要因它已經寫出很長的解釋，就批准下一個工具呼叫。先確認目標、範圍、權限與可回復性。

### 停止後的檢查

```bash
git status --short
git diff --stat
git diff
```

檢查部分寫入、未預期刪除、暫存檔、背景程序與建置產物。若代理呼叫過資料庫、Issue、部署或其他外部服務，還要到服務端確認副作用；Git diff 只涵蓋本機檔案。

### 繼續、分支或重開

- **繼續**：目標不變且變更可接受，使用 `opencode --continue`。
- **指定 Session**：以 `opencode --session <id>` 恢復特定工作。
- **分支**：使用 `--fork` 嘗試不同方案，並以 Git 隔離檔案。
- **重開**：需求改變、上下文混亂或權限要重設時，建立新 Session。

恢復時第一則訊息應包含已完成事項、不要重做的事項、目前測試結果與下一個驗收條件。

### 重試的界線

網路逾時可有限次重試；權限拒絕、語法錯誤、路徑錯誤與破壞性命令不應盲目重試。每次重試都要改變一個已知條件並記錄結果。更換 Provider 或 Model 後，重新執行測試，不能假設輸出等價。

### 中斷演練

在測試專案要求代理先提出計畫，不批准寫檔；接著中斷，檢查工作樹，再以 Session 繼續。第二次故意拒絕一個工具請求，觀察代理是否能回報權限失敗並等待新指示。這種演練比第一次遇到生產事故才學習更安全。

### 本節實作

使用 `examples/07-interrupt-resume/` 的檢查表，保存中斷前後的 `git status` 與 `git diff --stat`。若有外部副作用，另外記錄服務端確認結果。

### 本節練習

1. 列出三種必須立即中斷的工具請求。
2. 為網路逾時、權限拒絕與測試失敗各設計不同處理流程。
3. 寫一份能讓另一位工程師安全接手的 Session 摘要。

### 小結

停止、檢查、判斷恢復方式，再繼續，是安全的代理循環。Session 能保存上下文，但只有人員、測試與版本控制能決定哪些變更值得保留。

## Prompt Templates 與 Skills

### 本節目標

本章區分 Prompt、Command 與 Skill，並建立可重用、可測試、具有明確驗收條件的工作流程。

### 從指令到工作流程

一次性的 Prompt 適合簡單問題；當同一工作反覆出現，就應把目標、步驟、限制與驗收條件整理成可重用資源。Skill 不應只是更長的提示詞，而應像一份小型作業程序：說明輸入、允許的工具、不可做的事與完成定義。

例如，程式碼審查 Skill 可要求代理先讀取變更，再依正確性、安全性、測試與維護性分類問題，最後只回報可由檔案或測試證明的事項。

### 好 Skill 的結構

```md
# Review Changes

### Goal
Review the current diff without modifying files.

### Steps
1. Read the diff and relevant tests.
2. Check correctness, security, and regressions.
3. Report findings with file and line references.

### Constraints
Do not edit files or run destructive commands.

### Done when
Every finding has evidence or is marked as an open question.
```

把不可信的外部文字視為資料，而不是指示。Skill 也不能取代工具權限；即使文字要求唯讀，平台仍應在工具層阻擋未授權寫入。

### 版本與測試

Skill 是程式碼的一部分，應納入版本控制、附上範例輸入與預期輸出，並用代表性任務回歸測試。模型或 OpenCode 更新後，檢查 Skill 是否仍能使用相同工具與產生相同的驗收結果。

### 練習與小結

建立一個「失敗測試分析」Skill，要求先重現問題、不得直接刪除測試，最後提供最小修正建議。Skill 應封裝流程，不應偷偷擴大代理權限。

## 常用 Skills 實戰

### 本節目標

本章將常見開發工作轉為可重複的 Skills，並說明如何選擇 Skill，而不是安裝越多越好。

### 初學者優先順序

建議依下列順序建立：程式碼導覽、測試與除錯、變更審查、文件產生、Git 摘要。它們通常能提高效率，卻不必一開始就給予部署或資料庫寫入權限。

導覽 Skill 應輸出入口檔、資料流、相關測試與不確定之處；測試 Skill 應保留失敗證據；審查 Skill 應以 diff 為中心；文件 Skill 應標示未經驗證的敘述；Git Skill 應產生提交說明但不自行提交。

### 選擇 Skill 的四個問題

1. 這項工作是否每週重複？
2. 成功條件是否可以由測試或檔案驗證？
3. 是否需要固定的工具順序？
4. 失敗時是否有安全的回復方式？

若答案大多為否，先使用短 Prompt，不要過早抽象成 Skill。抽象的成本包括文件、版本、測試與維護。

### 實作規則

每個 Skill 都應記錄負責人、適用專案、版本與最後驗證日期。避免多個 Skill 同時改寫同一檔案；需要串接時，將前一個 Skill 的輸出定義為下一個 Skill 的輸入。

### 練習與小結

挑一項日常工作，先用 Prompt 執行三次，找出穩定步驟後再寫成 Skill。以五個代表性任務測試，記錄成功率、人工修正與所需權限。

## 內建工具與自訂工具

### 本節目標

理解工具如何把模型輸出的意圖轉成副作用，並以最小權限設計第一個可測試的自訂工具。

### 工具合約

工具合約至少描述名稱、輸入型別、輸出格式、可能錯誤、所需權限與是否具有副作用。輸入應拒絕不合法路徑、未知選項與過大範圍；輸出應包含狀態、摘要與可供下一步使用的資料。

把「搜尋」與「修改」分成兩個工具，通常比一個能任意執行 Shell 的工具安全。破壞性操作提供 dry-run，寫入前顯示目標檔案並要求確認。工具應避免把 API Key、完整環境變數或不必要的大型日誌回傳給模型。

### 自訂工具生命週期

模型提出 Tool Call 後，OpenCode 先驗證格式與權限，再執行工具，最後把成功或失敗結果寫回 Session。工具本身不應假設模型一定會正確使用輸入；所有邊界檢查必須在工具端完成。

### 測試策略

先寫不需要模型的單元測試：合法輸入、空結果、逾時、權限拒絕、路徑穿越與部分失敗。再用固定 Prompt 做整合測試，確認模型能理解工具說明，但不要以模型文字取代工具結果驗證。

### 練習與小結

設計一個唯讀的 `list_tests` 工具，只能搜尋專案測試目錄，並在輸入含有 `..` 或絕對路徑時拒絕。工具越小，越容易審查與重用。

## MCP 外部工具整合

### 本節目標

本章說明 MCP（Model Context Protocol）如何連接外部資料與工具，並建立安全的導入流程。

### MCP 的位置

MCP 將外部服務包裝成模型可使用的資源或工具。Filesystem 適合受限的檔案存取，GitHub／GitLab 適合 Issue 與 Pull Request，資料庫 MCP 適合查詢；各服務都應透過最小權限帳號提供。

MCP 不是安全邊界，也不是把任意服務交給模型的理由。每個 Server 都可能讀取資料、呼叫網路或產生副作用，因此要先確認來源、版本、授權範圍、日誌與撤銷方式。

### 導入流程

先在測試專案使用一個唯讀 Server，列出它暴露的工具，再逐一測試錯誤與逾時。禁止把生產資料庫、全家目錄或廣泛寫入權限一次交給代理。若服務需要 Token，使用憑證管理，不要把 Token 放入 `opencode.json`。

### Skills 與 MCP 的分工

Skill 描述「如何完成工作」；MCP 提供「可使用的外部能力」。例如文件研究 Skill 可以要求先搜尋、再引用來源、最後標出不確定性；Search MCP 則負責實際查詢。分工清楚後，同一 Skill 可以替換不同 MCP Server。

### 練習與小結

選一個唯讀外部服務，畫出資料流與權限範圍，寫出撤銷 Token 的方法。只有完成審查後，才加入需要寫入的操作。

## 事件與生命週期

### 本節目標

本章建立事件觀測模型，讓開發者能追蹤 Session、模型請求、工具執行、中斷與錯誤，而不把機密寫入日誌。

### 事件類型

有用的事件包括 Session 建立與恢復、訊息送出、模型回應、Tool 開始與結束、權限要求、錯誤及取消。每個事件應有時間、Session ID、請求 ID、名稱與狀態；事件順序比漂亮的文字日誌更有助於重建問題。

### 觀測與副作用

事件監聽器適合記錄耗時、統計工具成功率、更新 UI 或執行審計；不應偷偷改寫模型訊息或阻塞主迴圈。完整 Prompt、原始碼、環境變數與工具輸出可能含敏感資訊，集中式日誌應採遮罩、取樣與保留期限。

### 中斷與錯誤

取消事件應能傳播到正在等待的模型請求與工具。事件處理失敗時，不可讓觀測功能反過來使代理崩潰；採用隔離、逾時與降級。工具逾時、Provider 失效與權限拒絕應使用不同錯誤類型，方便決定是否重試。

### 練習與小結

為一次測試任務設計事件表，至少記錄 Session ID、模型、工具、耗時與結果狀態；檢查表中沒有 API Key 或原始碼。

## Extension 架構

### 本節目標

本章以 Extension-first 思維設計可替換、可測試、可升級的擴充功能。

### 核心與擴充的邊界

核心保留 Session、上下文、權限與事件等穩定協調能力；領域功能則放到 Tool、Skill、MCP、Plugin 或外部 Client。邊界的判斷問題是：「這項能力是否所有使用者都需要？是否依賴特定服務？是否可用獨立版本測試？」答案若是否定，多半不應塞進核心。

### Extension 合約

一個 Extension 應有明確入口、設定、依賴、版本、錯誤行為與移除方式。避免依賴未公開的內部資料結構；需要狀態時使用明確的儲存介面，並說明並行與重試語意。

### 升級與相容性

記錄支援的 OpenCode 版本與 Provider，建立最小整合測試。升級前在隔離專案驗證載入、工具呼叫、Session 恢復與錯誤處理。若 API 改變，提供遷移說明，不要只要求使用者刪除設定重新開始。

### 練習與小結

把一個「審查 Git diff」需求分別設計成 Prompt、Skill 與 Plugin，比較三者的責任、測試方式與權限。選擇最小而足夠的抽象層。

## 實用擴充模式

### 本節目標

從實際需求選擇自訂 Command、Agent、Tool、Provider Adapter、事件 Hook 或 MCP，而不是為了擴充而擴充。

### 常見模式

- **Command**：固定入口與固定 Prompt。
- **Agent**：具有特定角色、模型與工具權限的工作者。
- **Tool**：執行一個可驗證的動作。
- **Provider Adapter**：把內部模型閘道接到標準模型介面。
- **Event Hook**：記錄、審計或阻擋特定生命週期事件。
- **MCP Server**：把外部資料或服務提供給多個客戶端。

### 從痛點開始

例如團隊每次 Pull Request 都要整理測試結果：先用短 Prompt 驗證需求，再封裝成 Skill；若需要讀取 CI API，加入唯讀 MCP；若要在提交前強制檢查，才考慮事件 Hook。每一步都應保留可退回的簡單版本。

### 失敗設計

擴充功能最常見的問題不是功能不存在，而是失敗時沒有清楚回報。每個擴充都應說明服務離線、權限不足、輸入不完整與版本不相容時的訊息；破壞性動作應預設拒絕，而不是預設批准。

### 練習與小結

為「產生每日開發摘要」設計一個 Skill 加唯讀工具，再列出若要改寫 Issue 時需要增加的權限與人工確認。

## 替換終端機 UI

### 本節目標

理解 TUI 只是客戶端之一，並規劃 Web、桌面、遠端或非互動介面需要的事件、權限與取消機制。

### UI 與核心分離

介面負責顯示訊息、工具確認、Session 列表、串流狀態與錯誤；核心服務負責模型、工具、權限與持久化。不要在畫面元件內直接執行 Shell，也不要以「隱藏按鈕」繞過權限確認。

### 必備互動

替代 UI 至少要能顯示目前 Session、模型、正在執行的工具、工具輸入摘要、取消按鈕與最終結果。工具執行時間較長時，UI 應顯示進度與逾時，而不是讓使用者以為程式掛起。

### 遠端與非互動執行

`opencode run` 適合腳本，但腳本必須明確設定工作目錄、輸入、輸出與退出碼。Web 或遠端服務則需增加身分驗證、租戶隔離、CORS、請求取消與日誌遮罩。不可把本機 TUI 的信任模型直接搬到網路服務。

### 練習與小結

設計一個最小 Web Client 的狀態圖：Idle、Waiting、Tool Approval、Running、Completed、Failed、Cancelled。為每個轉移定義觸發事件與可見訊息。

## SDK 整合

### 本節目標

本章說明如何把 Agent 嵌入既有應用程式，並在產品層明確管理 Session、工具、權限、取消與錯誤。

### 先定義責任

應用程式必須決定誰建立與保存 Session、哪些工具可用、哪些操作需要人工批准，以及如何顯示串流回覆。不要把 TUI 的互動假設直接搬到後端服務；產品需要自己的身分、租戶與資料保留策略。

### 最小整合介面

一個可維護的整合至少需要建立／恢復 Session、送出訊息、訂閱模型與工具事件、取消工作、取得最終結果及追蹤 request ID。每一個請求都應綁定使用者、專案與權限範圍。

### 逐步導入

先以單一使用者、唯讀工具與測試 Provider 驗證流程，再加入寫檔、外部 API 與多租戶。所有模型輸出都視為不可信建議；資料庫、部署與付款等副作用必須由產品服務再次驗證。

### 練習與小結

設計一個只讀程式碼問答服務的介面契約，列出 Session、取消、錯誤、權限與日誌欄位。先完成契約，再選 SDK 實作。

## JSONL RPC

### 本節目標

本章以 JSON Lines 建立跨程序 Agent Client，處理請求、回覆、事件串流、逾時、取消與重連。

### 每行一個訊息

JSONL 的優點是簡單、可串流、容易由不同語言讀寫。Client 以 request ID 對應回覆；事件可以在回覆前後抵達，因此不能假設「一個請求只產生一行輸出」。每行都要驗證 JSON 結構，不能把未解析的文字直接當成命令執行。

### 可靠性

為請求設定逾時與取消訊號，區分網路失敗、Provider 錯誤、工具拒絕與輸入驗證錯誤。重連後不要盲目重送具有副作用的請求；若必須重試，使用冪等鍵或先查詢上一個 request ID 的狀態。

### 安全邊界

RPC Server 不應暴露本機任意路徑或無限制 Shell。每個連線要完成身分驗證、租戶隔離與權限判斷；錯誤回覆不應包含環境變數、完整 Prompt 或內部堆疊。

### 練習與小結

寫一個 Client 狀態機，涵蓋 Connected、Waiting、Streaming、Cancelled、Failed 與 Reconnecting，並為每種狀態設計可安全重試的規則。

## Package 發佈與維護

### 本節目標

本章建立可安裝、可升級、可移除且能說明安全風險的擴充 Package。

### 發佈內容

Package 應包含入口、版本、授權、依賴、設定範例、最小使用案例、相容性聲明與變更紀錄。安裝文件要說明需要的帳號、網路、檔案與外部服務權限，也要提供移除方式。

### 版本策略

鎖定可測試的 OpenCode 版本範圍與依賴版本；不要用 `latest` 取代驗證。每次更新至少測試載入、設定、Tool Call、Session 恢復與錯誤處理。若設定鍵或事件語意改變，提供遷移步驟。

### 供應鏈安全

檢查依賴來源與授權，建立 lockfile，避免安裝腳本執行不必要命令。Package 不應在未告知下上傳 Prompt、程式碼或使用統計；若需要遙測，必須提供說明與停用方法。

### 練習與小結

為一個 Skill Package 撰寫 README，包含安裝、設定、最小範例、權限、移除、相容性與問題回報方式。



# 完整實戰與工具選擇

## 完整實戰專案

### 本節目標

本章整合前面概念，建立一個受控的程式庫維護助理：它能探索、分析測試、提出修改計畫，經批准後才修改，最後回報證據。

### 專案規格

Agent 必須在專案根目錄工作，只能讀取原始碼與測試；修改前要列出檔案；執行測試後要回報命令與退出狀態；不得讀取秘密或自行部署。將這些規則寫入 `AGENTS.md`，模型設定與可共享選項寫入專案設定檔。

### 建置順序

先用一個模型完成唯讀導覽，再加入測試與搜尋 Tool，接著加入「失敗測試分析」Skill。每一層都先寫測試與錯誤案例，最後才接 MCP 或 SDK。此順序讓問題容易定位，也避免一次授予過多權限。

### 驗收流程

每次任務都保存需求、計畫、修改檔案、測試結果與風險。由人員閱讀 diff，確認沒有越界檔案、秘密或不必要重構；只有驗收通過才提交 Git。若任務中斷，從交接摘要恢復，而不是重新猜測狀態。

### 練習與小結

完成一個小型 bug 修正，交付 Session 摘要、Git diff、測試輸出與安全檢查表。再故意拒絕一個工具請求，觀察 Agent 如何處理權限失敗。

## OpenCode 與主流工具比較

### 本節目標

本章不追逐短期模型排行榜，而從工作流、控制力、整合與治理需求選擇工具。

### 選擇面向

比較終端機或 IDE、Provider 彈性、Session 恢復、Tool／Skill／MCP 擴充、SDK／RPC、權限模型、隱私、成本與學習曲線。版本更新後應重新確認功能，不把本章視為永久規格表。

### 適用情境

OpenCode 適合偏好終端機、需要多 Provider、希望自訂工具與 MCP，或要把代理嵌入應用程式的人。Claude Code 與 Aider 也適合終端機工作流；Cursor、Windsurf 等 IDE 工具適合需要編輯器整合、補全與視覺操作的人；GitHub Copilot 適合深度使用 GitHub 生態的團隊。

### 不適用情境

若需求只有 IDE 補全，建立完整 Extension-first 平台可能過度複雜；若團隊沒有能力維護權限、Provider 與擴充版本，單純的託管工具可能更合適。工具不會消除人工審查、測試與資料治理的責任。

### 練習與小結

以你的團隊需求評分三個工具：工作流、整合、隱私、成本與維護。說明每個分數的證據，而不是只引用品牌印象。



# 安全性與設計哲學

<!-- 正式稿章節；範例與勘誤見 https://github.com/t945935/opencode-deep-dive -->

## 最佳實務與安全性

### 本節目標

建立能被團隊治理的代理工作流：最小權限、可觀測、可測試、可停止、可恢復。

### 權限與資料

工具預設唯讀，寫入與外部服務操作要求明確批准。使用路徑白名單、沙箱、dry-run 與可還原 Git 工作流。API Key、Token、客戶資料與生產日誌不得進入 Prompt、Session 匯出或公開日誌。

### Prompt Injection

Issue、網頁、文件與程式碼中的文字都是不可信資料；它們不能提升工具權限、改寫系統規則或要求外傳秘密。將外部內容與真正指示分開，重要動作由平台再次驗證，不能只依賴模型「遵守提示」。

### 測試與觀測

除了一般單元與整合測試，還要建立代表性 Agent 任務、權限拒絕、工具逾時、Provider 失敗與惡意輸入案例。追蹤任務完成率、工具成功率、耗時、Token、成本與取消率；日誌採遮罩、取樣與保留期限。

### 小結

安全不是最後增加的選項，而是 Tool、MCP、Session、UI 與 RPC 每一層都要實作的約束。

<!-- 正式稿章節；範例與勘誤見 https://github.com/t945935/opencode-deep-dive -->

## OpenCode 的設計哲學

### 精簡核心

模型、介面與外部服務都會改變；Session、上下文、權限與事件邊界則應保持可理解。精簡核心不是功能少，而是把變動性留在可替換的層。

### 能力外置與組合

Prompt、Skill、Tool、MCP、Plugin、SDK 與 RPC 各自解決不同問題。能力外置可以獨立版本化、測試與移除，也讓同一工作流程跨越不同模型與介面。

### 人員仍是決策者

好的代理系統不以取得最多權限為目標，而是讓人員能理解、檢查、停止、恢復與替換它。模型可以加速探索與實作，但測試、審查、資料治理與最終責任仍屬於工程團隊。

### 結語

從一個唯讀任務開始，逐步加入模型、Session、Tool、Skill、MCP 與 Extension；每一步都保留證據與退路。這套方法比追逐某個暫時熱門的模型更能長期使用。
