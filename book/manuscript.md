# 第 1 章　OpenCode 是什麼

## 本章目標

讀完本章後，你應能說明 OpenCode 與單純聊天工具的差異，辨認 Provider、Model、Session、Tool、Skill、MCP 與 Extension 的責任，並在不修改檔案的前提下完成第一次探索。

## 1.1 從「問答」到「可執行的代理」

聊天模型通常只產生文字；程式設計代理則需要觀察專案、採取行動、讀取結果，再決定下一步。OpenCode 將這個過程組織成代理迴圈（Agent Loop）。模型負責理解目標與提出下一個動作，OpenCode 負責上下文組合、工具執行、權限確認、工作階段保存與回應呈現。

這個區分很重要。模型不應被視為可以任意操作電腦的使用者；它提出工具呼叫，平台依政策判斷是否允許，工具執行後再回傳結果。權限、紀錄與停止點都在模型之外。

## 1.2 六個核心角色

- **Provider**：連線與認證的模型服務。
- **Model**：Provider 提供的具體模型。
- **Session**：保存一段工作的訊息、工具結果與狀態。
- **Tool**：讀檔、搜尋、執行測試或呼叫服務的受控介面。
- **Skill／Command**：可重用的工作流程與指示。
- **MCP／Extension**：將外部服務或客製能力接入核心。

它們可以組合，但不應混為一談。把「如何做程式碼審查」寫成 Skill，把「執行測試」做成 Tool，把「連接 Issue 系統」交給 MCP，會比將所有邏輯塞進一個巨大 Prompt 更容易測試與維護。

## 1.3 精簡核心與擴充優先

OpenCode 的核心價值不是內建最多功能，而是提供可替換的邊界。模型會更新，團隊可能更換 Provider；互動介面可能是 TUI、Web 或自訂 Client；外部資料也可能來自 GitHub、資料庫或公司內部服務。若這些能力都緊密耦合在核心，任何變更都會造成連鎖影響。

擴充優先設計要求每項能力說清楚輸入、輸出、權限、生命週期與失敗行為。這也使讀者能先用簡單設定開始，再逐步加入工具，而不必一開始理解整個平台。

## 1.4 第一次安全探索

在一個沒有機密資料的 Git 專案根目錄執行：

```bash
opencode --version
opencode run "只列出專案的主要目錄與測試指令，不要修改任何檔案"
```

先閱讀回應與工具紀錄，確認代理使用的工作目錄、模型及工具。若輸出不符合預期，不要立即授予更多權限；先縮小問題、檢查設定，再重新執行。

## 章末練習

1. 為一個專案畫出 Provider、Session、Tool 與模型的關係圖。
2. 將「產生 Commit 訊息」分類為 Prompt、Skill 或 Tool，並說明理由。
3. 設計一個只能讀取 `src/` 的探索任務，列出它不應擁有的權限。

## 小結

OpenCode 是協調模型與受控能力的代理環境。理解角色邊界，是後續設定模型、恢復 Session、建立 Tool 與設計 Extension 的基礎。

# 第 2 章　安裝、啟動與基本操作

## 本章目標

本章建立一個可重現、可還原的 OpenCode 工作環境，並完成第一次唯讀任務。所有後續實作都應從這種安全基線開始。

## 2.1 安裝前檢查

先確認作業系統、終端機、Git 與 Node.js（若目前版本的安裝方式需要）符合官方文件。OpenCode 的 CLI 會持續更新，因此不要只複製網路文章中的安裝指令；先查看官方安裝頁，再以版本指令確認結果：

```bash
opencode --version
opencode --help
```

在 Windows WSL2 中，請注意目前工作目錄與檔案權限；需要 GUI 時另行確認 WSLg 或使用 Windows 端介面。無論平台為何，都應在專案根目錄啟動，避免代理誤讀相鄰專案。

## 2.2 建立安全的練習專案

```bash
mkdir opencode-lab && cd opencode-lab
git init
printf '# OpenCode Lab\n' > README.md
mkdir src tests
printf 'def add(a, b):\n    return a + b\n' > src/math.py
git add . && git commit -m 'Create practice project'
```

真實專案則應先確認 `git status`，並把未提交的個人修改保存好。代理產生的差異必須可透過 Git 審查或還原。

## 2.3 互動與一次性執行

在專案根目錄執行 `opencode` 可啟動互動式介面；`opencode run "任務"` 適合腳本、教學與可重現的單次工作。第一次請使用唯讀任務：

```bash
opencode run "找出 add 函式，說明它目前缺少哪些測試；不要修改檔案"
```

接著自行檢查回應是否引用真實檔案，而不是只接受流暢文字。當任務需要修改時，先要求代理提出計畫，再逐項批准。

## 2.4 啟動失敗的排查順序

遇到錯誤時依序檢查：命令是否在 `PATH`、版本是否符合、目前目錄是否正確、Provider 是否已登入、模型是否可用、設定檔是否有語法錯誤。用 `opencode debug --help` 查看當前版本支援的除錯功能；不要直接刪除 Session 或設定檔來「碰運氣」修復。

## 章末練習

- 建立一個乾淨練習專案並提交初始版本。
- 執行一次唯讀探索，再執行一次只修改測試的任務。
- 用 `git diff` 比較代理操作前後的變更。

## 小結

可靠的代理工作始於正確的工作目錄、乾淨的版本控制與小型可驗證任務。安裝只完成一半；真正的基線是能重現、能審查、能還原。

# 第 3 章　從請求到回應：Agent Loop

## 本章目標

本章用一次小任務追蹤代理迴圈，理解訊息、工具、權限與回應如何往返，並知道為何「模型說完成」不等於「任務已驗證」。

## 3.1 迴圈的六個步驟

1. 使用者提出目標、範圍與限制。
2. OpenCode 建立或恢復 Session，組合系統指示、專案規則與歷史。
3. Provider 將請求送給 Model。
4. Model 回傳文字，或提出 Tool Call。
5. OpenCode 檢查權限並執行獲准的工具。
6. 工具結果回到上下文，模型決定回答、修正或再次呼叫工具。

這不是模型內部的「思考內容」展示，而是可觀察的協作流程。設計工具時應讓每次呼叫都有清楚的名稱、輸入、輸出與失敗狀態。

## 3.2 一個可驗證的任務

```bash
opencode run "找出所有 Python 測試檔案，列出測試指令；不要修改檔案，也不要執行命令"
```

任務同時指定目標與負面限制。代理若仍嘗試寫檔或執行命令，使用者應拒絕工具請求並縮小 Prompt，而不是默許偏離行為。完成後，以自己熟悉的 Shell 指令驗證檔案清單與測試指令。

## 3.3 工具結果是上下文

讀取檔案、搜尋結果與測試日誌都會增加上下文。過長的輸出會降低模型注意力，也可能增加成本。工具應優先回傳摘要、錯誤位置與必要片段；完整結果可保存到檔案，僅在需要時讀取。

修改任務應分為探索、計畫、實作、測試與審查。每一階段都有明確出口，例如「列出將修改的檔案」或「測試通過並顯示命令」。這比一個含糊的「把這個功能做好」容易控制。

## 3.4 中斷與錯誤

網路錯誤、工具失敗、權限拒絕與使用者取消都可能終止迴圈。失敗後不要自動重試破壞性操作；先查看 Session、Git diff、測試結果與背景程序。若可安全恢復，保留上下文再繼續；若目標已改變，建立新 Session。

## 章末練習

畫出「要求修正一個失敗測試」的五階段流程，為每階段寫一個驗收條件。再設計一個工具，使它在 dry-run 模式下只報告將修改的檔案。

## 小結

Agent Loop 是「模型提出、平台執行、結果回饋」的循環。工具權限、輸出大小、驗收條件與中斷策略，決定了它是否可控。

# 第 4 章　設定檔放哪裡

## 本章目標

本章建立可追蹤的設定層次，說明全域設定、專案設定、`AGENTS.md` 與 `.opencode/` 的責任，並避免把機密資料提交到儲存庫。

## 4.1 先查版本，再查文件

設定鍵與搜尋順序可能隨 OpenCode 版本改變。本書範例以目前驗證版本為基線，但實作前仍應執行：

```bash
opencode --version
opencode --help
```

設定檔的 JSON Schema 可協助編輯器提示欄位與型別。不要因網路文章使用另一個版本，就假設所有欄位都仍可用。

## 4.2 全域與專案位置

個人預設通常放在使用者設定目錄，例如 Linux 的 `~/.config/opencode/opencode.json` 或 `.jsonc`；專案共用設定放在目前專案根目錄的 `opencode.json` 或 `opencode.jsonc`。專案根目錄是包含 `.git` 的目錄，而不是 `src/`、`dist/` 或任意目前子目錄。

`AGENTS.md` 用於人類可讀的規則：測試命令、格式化要求、不可觸碰的路徑與完成定義。`opencode.json` 則較適合機器可讀的模型、Provider 或功能設定。自訂 Agent、Command、Skill 與 Plugin 的具體目錄，務必依當前官方文件確認。

## 4.3 最小設定

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "model": "provider/model-name"
}
```

`provider/model-name` 只是佔位值；使用 `opencode models` 查詢帳號實際可用的 ID。API Key 不應放進 JSON；把憑證管理與專案設定分開，才能安全提交設定檔。

## 4.4 設定衝突的排查

當實際模型或行為與預期不同，記錄：啟動所在目錄、使用的設定檔、命令列參數、環境變數與版本。一次只改一項，重新執行一個短任務，再比較結果。這種實驗式排查比同時修改多個檔案可靠。

## 章末練習

建立一份不含秘密的專案設定，加入 `AGENTS.md` 指定測試命令，並寫一個任務要求代理先讀規則再回答。將設定檔加入 Git，確認 `git diff` 沒有出現 Token。

## 小結

全域設定服務個人偏好，專案根目錄設定服務團隊共識，`AGENTS.md` 描述工作規則。清楚的放置位置與優先順序，是可重現代理行為的前提。

# 第 5 章　LLM Provider 與模型選擇

## 本章目標

本章說明 Provider、Model 與 API 憑證的關係，提供初學者一至三個選擇，並建立可切換、可控成本且不洩漏機密的模型策略。

## 5.1 Provider 與 Model

Provider 是提供模型與帳務的服務；Model 是該服務中的具體版本。OpenCode 將兩者以 `provider/model` 形式識別。先用 `opencode providers` 管理登入或憑證，再用 `opencode models [provider]` 查詢目前帳號可用的模型。不要把書中的模型 ID 視為永久不變的名稱。

## 5.2 初學者三種選擇

- **Claude Sonnet 系列**：適合一般程式開發、重構、除錯與工具協作，作為單一主力模型通常容易開始。
- **OpenAI GPT 系列**：適合多用途開發、文件與既有服務整合；先選帳號實際可用的穩定版本。
- **Gemini Pro 系列**：適合長文件或大型程式庫探索；仍應以實際工具呼叫品質與費用測試為準。

初學者應先選一個主力模型，不要同時研究十個 Provider。第二個模型可用於備援或審查；低成本模型則適合摘要、格式整理與簡單文件工作。模型選擇必須同時考慮品質、速度、上下文成本與原始碼傳輸政策。

## 5.3 設定與單次切換

專案設定可使用：

```json
{
  "$schema": "https://opencode.ai/config.json",
  "model": "provider/model-name"
}
```

當次任務可用 CLI 覆寫：

```bash
opencode run -m provider/model-name "只分析測試失敗原因，不要修改檔案"
```

請將實際模型 ID 替換為 `opencode models` 顯示的值。模型選擇範例位於 [`examples/05-model-selection/`](../../examples/05-model-selection/)。

## 5.4 憑證與安全

API Key 不可寫進 `opencode.json`、Skill、Prompt 或 Git。使用 OpenCode 支援的 Provider 登入流程、環境變數或作業系統憑證管理。若專案含客戶程式碼，先確認公司的資料政策與 Provider 的保留政策；必要時採本機模型或遮蔽敏感資料。

## 5.5 Fallback 與評估

Provider 暫時失效時，先保留 Session 與已完成的測試結果，再切換備援模型。切換後不可假設輸出等價，重要修改仍須重新執行測試。可建立十個代表性任務，記錄成功率、耗時、Token、費用、工具錯誤與人工修正量，以資料而不是印象選模型。

## 章末練習

1. 用 `opencode models` 找出帳號可用模型，挑一個主力與一個備援。
2. 建立不含憑證的 `opencode.jsonc`，執行一次唯讀任務。
3. 比較兩個模型完成相同測試修正任務的時間、diff 大小與測試結果。

## 小結

模型是可替換的服務元件。初學者從一個穩定主力開始，以專案設定記錄策略，以 CLI 在單次任務切換，並用測試與成本資料驗證選擇。

# 第 6 章　Session、訊息樹與上下文

## 本章目標

理解 Session 如何保存工作、訊息樹如何表達分支，以及上下文壓縮如何影響長任務。讀者將學會在繼續、分支與重新開始之間做選擇。

## 6.1 Session 是什麼

Session 不只是聊天紀錄，而是一次代理工作的可恢復邊界。它通常包含使用者訊息、模型回覆、工具呼叫、工具結果與相關狀態。工作是否可恢復，取決於這些內容是否被持久保存，以及工具本身是否可安全重做。

## 6.2 訊息樹與分支

若從某個歷史節點嘗試另一種方案，應建立分支而不是覆蓋原工作。分支讓兩組 Prompt、工具結果與 diff 可以比較；但分支不代表檔案系統自動隔離，因此仍要用 Git worktree、分支或暫存目錄隔離實際修改。

## 6.3 上下文容量

模型上下文由系統指示、專案規則、對話歷史、檔案片段與工具輸出組成。當內容接近上限，平台可能摘要或壓縮較早訊息。摘要若遺漏限制、測試結果或未完成事項，後續代理就可能重複工作或作出錯誤假設。

長任務每完成一個里程碑，就留下交接摘要：目標、已修改檔案、目前測試、未完成工作、已知風險與下一步。只讀取與當前任務相關的檔案，避免把整個 `node_modules`、建置輸出或大型日誌塞進上下文。

## 6.4 保存可恢復性

工具結果應包含命令、退出狀態與短摘要；重要產物應保存於可追蹤檔案。這樣即使模型切換或 Session 恢復，也能用檔案與測試重新建立事實，而非依賴記憶。

## 章末練習

建立一個包含三個里程碑的任務，在每個里程碑寫交接摘要。接著以不同方向建立分支，使用 Git diff 比較兩條路線，最後只保留測試通過者。

## 小結

Session 保存歷史，上下文決定模型當下看見什麼，Git 保存實際變更。三者各有責任，不能用聊天歷史取代版本控制。

# 第 7 章　中斷、停止與重新開始

## 本章目標

中斷代理是正常的控制手段，不是例外。讀者將學會在危險操作、偏離目標、成本過高或服務失敗時停止，並安全地恢復或重新規劃工作。

## 7.1 何時應中斷

看到代理準備修改範圍外的檔案、執行不理解的命令、讀取機密、反覆重試或產生大量無關輸出時，應立即停止。先問「這個動作是否符合原始目標、是否可還原、是否需要我的批准」，不要因代理已經解釋一大段就放棄控制。

## 7.2 停止後的檢查

```bash
git status --short
git diff --stat
git diff
```

確認是否有部分寫入、未預期的刪除、背景程序、產生的暫存檔或測試資料。若工具執行了資料庫、部署或外部 API 操作，還要到服務端確認副作用；Git diff 不能涵蓋所有外部變更。

## 7.3 繼續、分支或重開

- **繼續**：目標不變、現有變更可接受，使用 `opencode --continue`。
- **指定 Session**：需要恢復較早工作時，使用 `opencode --session <id>`。
- **分支**：想嘗試不同方案而保留原歷史時，搭配 `--fork`，並以 Git 隔離檔案。
- **重開**：上下文已混亂、需求已改變或權限策略要重設時，建立新 Session。

恢復前先寫一段短摘要，明確指出「已完成什麼、不要重做什麼、下一個驗收條件」。

## 7.4 重試的界線

網路逾時可有限次重試；權限拒絕、語法錯誤或破壞性命令不應盲目重試。每次重試都應改變一個已知條件，並記錄結果。若切換 Provider 或 Model，重新驗證重要輸出。

## 章末練習

模擬一次測試修正任務：在代理提出修改計畫後中斷，檢查 Git 狀態，再以 Session 繼續。另建立一個分支方案，記錄兩種方案的測試與風險差異。

## 小結

停止、檢查、決定恢復方式，再繼續，是安全的代理工作循環。Session 能保存上下文，但只有人員與版本控制能決定哪些變更值得保留。

# 第 8 章　Prompt Templates 與 Skills

## 本章目標

本章區分 Prompt、Command 與 Skill，並建立可重用、可測試、具有明確驗收條件的工作流程。

## 8.1 從指令到工作流程

一次性的 Prompt 適合簡單問題；當同一工作反覆出現，就應把目標、步驟、限制與驗收條件整理成可重用資源。Skill 不應只是更長的提示詞，而應像一份小型作業程序：說明輸入、允許的工具、不可做的事與完成定義。

例如，程式碼審查 Skill 可要求代理先讀取變更，再依正確性、安全性、測試與維護性分類問題，最後只回報可由檔案或測試證明的事項。

## 8.2 好 Skill 的結構

```md
# Review Changes

## Goal
Review the current diff without modifying files.

## Steps
1. Read the diff and relevant tests.
2. Check correctness, security, and regressions.
3. Report findings with file and line references.

## Constraints
Do not edit files or run destructive commands.

## Done when
Every finding has evidence or is marked as an open question.
```

把不可信的外部文字視為資料，而不是指示。Skill 也不能取代工具權限；即使文字要求唯讀，平台仍應在工具層阻擋未授權寫入。

## 8.3 版本與測試

Skill 是程式碼的一部分，應納入版本控制、附上範例輸入與預期輸出，並用代表性任務回歸測試。模型或 OpenCode 更新後，檢查 Skill 是否仍能使用相同工具與產生相同的驗收結果。

## 練習與小結

建立一個「失敗測試分析」Skill，要求先重現問題、不得直接刪除測試，最後提供最小修正建議。Skill 應封裝流程，不應偷偷擴大代理權限。

# 第 9 章　常用 Skills 實戰

## 本章目標

本章將常見開發工作轉為可重複的 Skills，並說明如何選擇 Skill，而不是安裝越多越好。

## 9.1 初學者優先順序

建議依下列順序建立：程式碼導覽、測試與除錯、變更審查、文件產生、Git 摘要。它們通常能提高效率，卻不必一開始就給予部署或資料庫寫入權限。

導覽 Skill 應輸出入口檔、資料流、相關測試與不確定之處；測試 Skill 應保留失敗證據；審查 Skill 應以 diff 為中心；文件 Skill 應標示未經驗證的敘述；Git Skill 應產生提交說明但不自行提交。

## 9.2 選擇 Skill 的四個問題

1. 這項工作是否每週重複？
2. 成功條件是否可以由測試或檔案驗證？
3. 是否需要固定的工具順序？
4. 失敗時是否有安全的回復方式？

若答案大多為否，先使用短 Prompt，不要過早抽象成 Skill。抽象的成本包括文件、版本、測試與維護。

## 9.3 實作規則

每個 Skill 都應記錄負責人、適用專案、版本與最後驗證日期。避免多個 Skill 同時改寫同一檔案；需要串接時，將前一個 Skill 的輸出定義為下一個 Skill 的輸入。

## 練習與小結

挑一項日常工作，先用 Prompt 執行三次，找出穩定步驟後再寫成 Skill。以五個代表性任務測試，記錄成功率、人工修正與所需權限。

# 第 10 章　內建工具與自訂工具

## 本章目標

理解工具如何把模型輸出的意圖轉成副作用，並以最小權限設計第一個可測試的自訂工具。

## 10.1 工具合約

工具合約至少描述名稱、輸入型別、輸出格式、可能錯誤、所需權限與是否具有副作用。輸入應拒絕不合法路徑、未知選項與過大範圍；輸出應包含狀態、摘要與可供下一步使用的資料。

把「搜尋」與「修改」分成兩個工具，通常比一個能任意執行 Shell 的工具安全。破壞性操作提供 dry-run，寫入前顯示目標檔案並要求確認。工具應避免把 API Key、完整環境變數或不必要的大型日誌回傳給模型。

## 10.2 自訂工具生命週期

模型提出 Tool Call 後，OpenCode 先驗證格式與權限，再執行工具，最後把成功或失敗結果寫回 Session。工具本身不應假設模型一定會正確使用輸入；所有邊界檢查必須在工具端完成。

## 10.3 測試策略

先寫不需要模型的單元測試：合法輸入、空結果、逾時、權限拒絕、路徑穿越與部分失敗。再用固定 Prompt 做整合測試，確認模型能理解工具說明，但不要以模型文字取代工具結果驗證。

## 練習與小結

設計一個唯讀的 `list_tests` 工具，只能搜尋專案測試目錄，並在輸入含有 `..` 或絕對路徑時拒絕。工具越小，越容易審查與重用。

# 第 11 章　MCP 外部工具整合

## 本章目標

本章說明 MCP（Model Context Protocol）如何連接外部資料與工具，並建立安全的導入流程。

## 11.1 MCP 的位置

MCP 將外部服務包裝成模型可使用的資源或工具。Filesystem 適合受限的檔案存取，GitHub／GitLab 適合 Issue 與 Pull Request，資料庫 MCP 適合查詢；各服務都應透過最小權限帳號提供。

MCP 不是安全邊界，也不是把任意服務交給模型的理由。每個 Server 都可能讀取資料、呼叫網路或產生副作用，因此要先確認來源、版本、授權範圍、日誌與撤銷方式。

## 11.2 導入流程

先在測試專案使用一個唯讀 Server，列出它暴露的工具，再逐一測試錯誤與逾時。禁止把生產資料庫、全家目錄或廣泛寫入權限一次交給代理。若服務需要 Token，使用憑證管理，不要把 Token 放入 `opencode.json`。

## 11.3 Skills 與 MCP 的分工

Skill 描述「如何完成工作」；MCP 提供「可使用的外部能力」。例如文件研究 Skill 可以要求先搜尋、再引用來源、最後標出不確定性；Search MCP 則負責實際查詢。分工清楚後，同一 Skill 可以替換不同 MCP Server。

## 練習與小結

選一個唯讀外部服務，畫出資料流與權限範圍，寫出撤銷 Token 的方法。只有完成審查後，才加入需要寫入的操作。

# 第 12 章　事件與生命週期

## 本章目標

本章建立事件觀測模型，讓開發者能追蹤 Session、模型請求、工具執行、中斷與錯誤，而不把機密寫入日誌。

## 12.1 事件類型

有用的事件包括 Session 建立與恢復、訊息送出、模型回應、Tool 開始與結束、權限要求、錯誤及取消。每個事件應有時間、Session ID、請求 ID、名稱與狀態；事件順序比漂亮的文字日誌更有助於重建問題。

## 12.2 觀測與副作用

事件監聽器適合記錄耗時、統計工具成功率、更新 UI 或執行審計；不應偷偷改寫模型訊息或阻塞主迴圈。完整 Prompt、原始碼、環境變數與工具輸出可能含敏感資訊，集中式日誌應採遮罩、取樣與保留期限。

## 12.3 中斷與錯誤

取消事件應能傳播到正在等待的模型請求與工具。事件處理失敗時，不可讓觀測功能反過來使代理崩潰；採用隔離、逾時與降級。工具逾時、Provider 失效與權限拒絕應使用不同錯誤類型，方便決定是否重試。

## 練習與小結

為一次測試任務設計事件表，至少記錄 Session ID、模型、工具、耗時與結果狀態；檢查表中沒有 API Key 或原始碼。

# 第 13 章　Extension 架構

## 本章目標

本章以 Extension-first 思維設計可替換、可測試、可升級的擴充功能。

## 13.1 核心與擴充的邊界

核心保留 Session、上下文、權限與事件等穩定協調能力；領域功能則放到 Tool、Skill、MCP、Plugin 或外部 Client。邊界的判斷問題是：「這項能力是否所有使用者都需要？是否依賴特定服務？是否可用獨立版本測試？」答案若是否定，多半不應塞進核心。

## 13.2 Extension 合約

一個 Extension 應有明確入口、設定、依賴、版本、錯誤行為與移除方式。避免依賴未公開的內部資料結構；需要狀態時使用明確的儲存介面，並說明並行與重試語意。

## 13.3 升級與相容性

記錄支援的 OpenCode 版本與 Provider，建立最小整合測試。升級前在隔離專案驗證載入、工具呼叫、Session 恢復與錯誤處理。若 API 改變，提供遷移說明，不要只要求使用者刪除設定重新開始。

## 練習與小結

把一個「審查 Git diff」需求分別設計成 Prompt、Skill 與 Plugin，比較三者的責任、測試方式與權限。選擇最小而足夠的抽象層。

# 第 14 章　實用擴充模式

## 本章目標

從實際需求選擇自訂 Command、Agent、Tool、Provider Adapter、事件 Hook 或 MCP，而不是為了擴充而擴充。

## 14.1 常見模式

- **Command**：固定入口與固定 Prompt。
- **Agent**：具有特定角色、模型與工具權限的工作者。
- **Tool**：執行一個可驗證的動作。
- **Provider Adapter**：把內部模型閘道接到標準模型介面。
- **Event Hook**：記錄、審計或阻擋特定生命週期事件。
- **MCP Server**：把外部資料或服務提供給多個客戶端。

## 14.2 從痛點開始

例如團隊每次 Pull Request 都要整理測試結果：先用短 Prompt 驗證需求，再封裝成 Skill；若需要讀取 CI API，加入唯讀 MCP；若要在提交前強制檢查，才考慮事件 Hook。每一步都應保留可退回的簡單版本。

## 14.3 失敗設計

擴充功能最常見的問題不是功能不存在，而是失敗時沒有清楚回報。每個擴充都應說明服務離線、權限不足、輸入不完整與版本不相容時的訊息；破壞性動作應預設拒絕，而不是預設批准。

## 練習與小結

為「產生每日開發摘要」設計一個 Skill 加唯讀工具，再列出若要改寫 Issue 時需要增加的權限與人工確認。

# 第 15 章　替換終端機 UI

## 本章目標

理解 TUI 只是客戶端之一，並規劃 Web、桌面、遠端或非互動介面需要的事件、權限與取消機制。

## 15.1 UI 與核心分離

介面負責顯示訊息、工具確認、Session 列表、串流狀態與錯誤；核心服務負責模型、工具、權限與持久化。不要在畫面元件內直接執行 Shell，也不要以「隱藏按鈕」繞過權限確認。

## 15.2 必備互動

替代 UI 至少要能顯示目前 Session、模型、正在執行的工具、工具輸入摘要、取消按鈕與最終結果。工具執行時間較長時，UI 應顯示進度與逾時，而不是讓使用者以為程式掛起。

## 15.3 遠端與非互動執行

`opencode run` 適合腳本，但腳本必須明確設定工作目錄、輸入、輸出與退出碼。Web 或遠端服務則需增加身分驗證、租戶隔離、CORS、請求取消與日誌遮罩。不可把本機 TUI 的信任模型直接搬到網路服務。

## 練習與小結

設計一個最小 Web Client 的狀態圖：Idle、Waiting、Tool Approval、Running、Completed、Failed、Cancelled。為每個轉移定義觸發事件與可見訊息。

# 第 16 章　SDK 整合

## 本章目標

本章說明如何把 Agent 嵌入既有應用程式，並在產品層明確管理 Session、工具、權限、取消與錯誤。

## 16.1 先定義責任

應用程式必須決定誰建立與保存 Session、哪些工具可用、哪些操作需要人工批准，以及如何顯示串流回覆。不要把 TUI 的互動假設直接搬到後端服務；產品需要自己的身分、租戶與資料保留策略。

## 16.3 逐步導入

先以單一使用者、唯讀工具與測試 Provider 驗證流程，再加入寫檔、外部 API 與多租戶。所有模型輸出都視為不可信建議；資料庫、部署與付款等副作用必須由產品服務再次驗證。

## 練習與小結

# 第 17 章　JSONL RPC

## 本章目標

本章以 JSON Lines 建立跨程序 Agent Client，處理請求、回覆、事件串流、逾時、取消與重連。

## 17.1 每行一個訊息

JSONL 的優點是簡單、可串流、容易由不同語言讀寫。Client 以 request ID 對應回覆；事件可以在回覆前後抵達，因此不能假設「一個請求只產生一行輸出」。每行都要驗證 JSON 結構，不能把未解析的文字直接當成命令執行。

## 17.2 可靠性

為請求設定逾時與取消訊號，區分網路失敗、Provider 錯誤、工具拒絕與輸入驗證錯誤。重連後不要盲目重送具有副作用的請求；若必須重試，使用冪等鍵或先查詢上一個 request ID 的狀態。

## 17.3 安全邊界

RPC Server 不應暴露本機任意路徑或無限制 Shell。每個連線要完成身分驗證、租戶隔離與權限判斷；錯誤回覆不應包含環境變數、完整 Prompt 或內部堆疊。

## 練習與小結

寫一個 Client 狀態機，涵蓋 Connected、Waiting、Streaming、Cancelled、Failed 與 Reconnecting，並為每種狀態設計可安全重試的規則。

# 第 18 章　Package 發佈與維護

## 本章目標

本章建立可安裝、可升級、可移除且能說明安全風險的擴充 Package。

## 18.1 發佈內容

Package 應包含入口、版本、授權、依賴、設定範例、最小使用案例、相容性聲明與變更紀錄。安裝文件要說明需要的帳號、網路、檔案與外部服務權限，也要提供移除方式。

鎖定可測試的 OpenCode 版本範圍與依賴版本；不要用 `latest` 取代驗證。每次更新至少測試載入、設定、Tool Call、Session 恢復與錯誤處理。若設定鍵或事件語意改變，提供遷移步驟。

## 18.3 供應鏈安全

檢查依賴來源與授權，建立 lockfile，避免安裝腳本執行不必要命令。Package 不應在未告知下上傳 Prompt、程式碼或使用統計；若需要遙測，必須提供說明與停用方法。

為一個 Skill Package 撰寫 README，包含安裝、設定、最小範例、權限、移除、相容性與問題回報方式。

# 第 19 章　完整實戰專案

## 本章目標

本章整合前面概念，建立一個受控的程式庫維護助理：它能探索、分析測試、提出修改計畫，經批准後才修改，最後回報證據。

## 19.1 專案規格

Agent 必須在專案根目錄工作，只能讀取原始碼與測試；修改前要列出檔案；執行測試後要回報命令與退出狀態；不得讀取秘密或自行部署。將這些規則寫入 `AGENTS.md`，模型設定與可共享選項寫入專案設定檔。

## 19.2 建置順序

先用一個模型完成唯讀導覽，再加入測試與搜尋 Tool，接著加入「失敗測試分析」Skill。每一層都先寫測試與錯誤案例，最後才接 MCP 或 SDK。此順序讓問題容易定位，也避免一次授予過多權限。

## 19.3 驗收流程

每次任務都保存需求、計畫、修改檔案、測試結果與風險。由人員閱讀 diff，確認沒有越界檔案、秘密或不必要重構；只有驗收通過才提交 Git。若任務中斷，從交接摘要恢復，而不是重新猜測狀態。

## 練習與小結

完成一個小型 bug 修正，交付 Session 摘要、Git diff、測試輸出與安全檢查表。再故意拒絕一個工具請求，觀察 Agent 如何處理權限失敗。

# 第 20 章　OpenCode 與主流工具比較

## 本章目標

本章不追逐短期模型排行榜，而從工作流、控制力、整合與治理需求選擇工具。

## 20.1 選擇面向

比較終端機或 IDE、Provider 彈性、Session 恢復、Tool／Skill／MCP 擴充、SDK／RPC、權限模型、隱私、成本與學習曲線。版本更新後應重新確認功能，不把本章視為永久規格表。

## 20.2 適用情境

OpenCode 適合偏好終端機、需要多 Provider、希望自訂工具與 MCP，或要把代理嵌入應用程式的人。Claude Code 與 Aider 也適合終端機工作流；Cursor、Windsurf 等 IDE 工具適合需要編輯器整合、補全與視覺操作的人；GitHub Copilot 適合深度使用 GitHub 生態的團隊。

## 20.3 不適用情境

若需求只有 IDE 補全，建立完整 Extension-first 平台可能過度複雜；若團隊沒有能力維護權限、Provider 與擴充版本，單純的託管工具可能更合適。工具不會消除人工審查、測試與資料治理的責任。

## 練習與小結

以你的團隊需求評分三個工具：工作流、整合、隱私、成本與維護。說明每個分數的證據，而不是只引用品牌印象。

# 第 21 章　最佳實務與安全性

## 本章目標

建立能被團隊治理的代理工作流：最小權限、可觀測、可測試、可停止、可恢復。

## 21.1 權限與資料

工具預設唯讀，寫入與外部服務操作要求明確批准。使用路徑白名單、沙箱、dry-run 與可還原 Git 工作流。API Key、Token、客戶資料與生產日誌不得進入 Prompt、Session 匯出或公開日誌。

## 21.2 Prompt Injection

Issue、網頁、文件與程式碼中的文字都是不可信資料；它們不能提升工具權限、改寫系統規則或要求外傳秘密。將外部內容與真正指示分開，重要動作由平台再次驗證，不能只依賴模型「遵守提示」。

## 21.3 測試與觀測

除了一般單元與整合測試，還要建立代表性 Agent 任務、權限拒絕、工具逾時、Provider 失敗與惡意輸入案例。追蹤任務完成率、工具成功率、耗時、Token、成本與取消率；日誌採遮罩、取樣與保留期限。

## 小結

安全不是最後增加的選項，而是 Tool、MCP、Session、UI 與 RPC 每一層都要實作的約束。

# 第 22 章　OpenCode 的設計哲學

## 精簡核心

模型、介面與外部服務都會改變；Session、上下文、權限與事件邊界則應保持可理解。精簡核心不是功能少，而是把變動性留在可替換的層。

## 能力外置與組合

Prompt、Skill、Tool、MCP、Plugin、SDK 與 RPC 各自解決不同問題。能力外置可以獨立版本化、測試與移除，也讓同一工作流程跨越不同模型與介面。

## 人員仍是決策者

好的代理系統不以取得最多權限為目標，而是讓人員能理解、檢查、停止、恢復與替換它。模型可以加速探索與實作，但測試、審查、資料治理與最終責任仍屬於工程團隊。

## 結語

從一個唯讀任務開始，逐步加入模型、Session、Tool、Skill、MCP 與 Extension；每一步都保留證據與退路。這套方法比追逐某個暫時熱門的模型更能長期使用。
