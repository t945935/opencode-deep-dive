# 第 3 章　從請求到回應：Agent Loop

## 本章目標

本章逐步拆解代理迴圈，理解模型、工具、權限和上下文如何往返，並知道何時應中斷而不是繼續批准。

## 3.1 六個步驟

1. 使用者提出目標、範圍與限制。
2. OpenCode 建立或恢復 Session。
3. 平台組合系統指示、專案規則、歷史與相關檔案。
4. Provider 將 Context 送給 Model。
5. Model 回傳文字或提出 Tool Call；平台檢查權限後執行。
6. 工具結果寫回 Session，模型決定下一步或完成回答。

模型的「建議」與平台的「執行」是兩件事。這個邊界讓使用者可以拒絕危險工具，也讓系統能對所有 Client 套用相同的權限規則。

## 3.2 由唯讀任務開始

```bash
opencode run "找出所有測試檔案，列出測試指令；不要修改檔案，也不要執行命令"
```

任務同時提供正面目標和負面限制。完成後，以自己的命令驗證檔案清單；不要只因模型回答流暢，就認為它讀到了正確的專案。

## 3.3 工具合約與結果

工具應說明輸入型別、輸出格式、權限、錯誤與副作用。搜尋工具回傳檔案和行號即可；測試工具回傳命令、退出狀態和關鍵錯誤即可。把完整建置日誌全部送進上下文，會浪費 Token 並遮蔽真正問題。

對修改任務採取探索、計畫、修改、測試、審查五階段。每階段有一個可驗收出口，例如「列出將修改的檔案」或「測試命令退出碼為零」。

## 3.4 錯誤與中斷

工具失敗、Provider 逾時、權限拒絕與使用者取消都可能結束迴圈。網路逾時可以有限次重試；權限拒絕或破壞性命令不應盲目重試。中斷後先看 Git diff、背景程序與外部服務，再決定繼續、分支或重開 Session。

## 3.5 觀察一次完整工作

在測試專案要求代理「先提出計畫，不要修改」，記錄它讀取的檔案與請求的工具。批准一個低風險讀取工具後，再拒絕一個不必要的寫入工具。這個演練能讓你看見權限檢查是迴圈的一部分，而不是事後補救。

## 小結

Agent Loop 是「模型提出、平台執行、結果回饋」的循環。清楚的工具合約、有限的上下文、可驗收的階段與可中斷的權限，決定了代理是否可靠。
