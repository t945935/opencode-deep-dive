# 第 3 章　從請求到回應：Agent Loop

## 本章目標

本章用一次小任務追蹤代理迴圈，理解訊息、工具、權限與回應如何往返，並知道為何「模型說完成」不等於「任務已驗證」。

## 3.1 迴圈的六個步驟

1. 使用者提出目標、範圍與限制。
2. OpenCode 建立或恢復 Session，組合系統指示、專案規則與歷史。
3. Provider 將請求送給 Model。
4. Model 回傳文字，或提出 Tool Call。
5. OpenCode 檢查權限並執行獲准的工具。
6. 工具結果回到上下文，模型決定回答、修正或再次呼叫工具。

這不是模型內部的「思考內容」展示，而是可觀察的協作流程。設計工具時應讓每次呼叫都有清楚的名稱、輸入、輸出與失敗狀態。

## 3.2 一個可驗證的任務

```bash
opencode run "找出所有 Python 測試檔案，列出測試指令；不要修改檔案，也不要執行命令"
```

任務同時指定目標與負面限制。代理若仍嘗試寫檔或執行命令，使用者應拒絕工具請求並縮小 Prompt，而不是默許偏離行為。完成後，以自己熟悉的 Shell 指令驗證檔案清單與測試指令。

## 3.3 工具結果是上下文

讀取檔案、搜尋結果與測試日誌都會增加上下文。過長的輸出會降低模型注意力，也可能增加成本。工具應優先回傳摘要、錯誤位置與必要片段；完整結果可保存到檔案，僅在需要時讀取。

修改任務應分為探索、計畫、實作、測試與審查。每一階段都有明確出口，例如「列出將修改的檔案」或「測試通過並顯示命令」。這比一個含糊的「把這個功能做好」容易控制。

## 3.4 中斷與錯誤

網路錯誤、工具失敗、權限拒絕與使用者取消都可能終止迴圈。失敗後不要自動重試破壞性操作；先查看 Session、Git diff、測試結果與背景程序。若可安全恢復，保留上下文再繼續；若目標已改變，建立新 Session。

## 章末練習

畫出「要求修正一個失敗測試」的五階段流程，為每階段寫一個驗收條件。再設計一個工具，使它在 dry-run 模式下只報告將修改的檔案。

## 小結

Agent Loop 是「模型提出、平台執行、結果回饋」的循環。工具權限、輸出大小、驗收條件與中斷策略，決定了它是否可控。
